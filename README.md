# Тестовое задание — решение

Ночная синхронизация сущностей amoCRM (20 тыс. покупателей, 50 тыс. сделок) в Postgres.
Точка входа — `collect_leads_customers(is_full=True)` в `main.py`.

## Что было дорого в исходном варианте

- **Коммит и SELECT на каждую сущность.**
  Плюс `expire_on_commit=True`: после каждого коммита ORM
  перечитывал строку заново.
- **Поиск через JSONB `@>` без индексов** (`amo_customers @> [{general: {id: ...}}]`) —
  seq scan по всей таблице на каждую сущность.
- **`jsonb_set` по индексу с off-by-one** (`len(...) + 1` при вставке в конец):
  новые элементы терялись.
- **Чистка перечитывала всю таблицу** (`select(AbstractCustomer).all()`) в память
  и делала COMMIT на каждый атрибут каждой строки.
- **Падения/расхождения с правилами**: `lead_action` возвращал `None` после слияния
  (AttributeError + слитая сделка терялась при чистке), фильтр имени падал на `None`
  и проверял не ту переменную цикла, при ошибках сбора чистка всё равно запускалась,
  у клиента CRM отсутствовали `BaseEntity.get_schema()`/`as_dict()` — прогон падал сразу.

## Что изменено

### Схема (нормализация)

- `abstract_customer` — агрегат покупателя (id, send_methods, created_at, updated_at).
- `amo_customer`, `amo_lead` — `crm_id` (UNIQUE), `abstract_customer_id` (FK, CASCADE),
  `login` (индекс), `name` (индекс), `api_value` JSONB — сырой ответ API, формат JSON сохранён.
- `amo_contact`, `amo_company` — `crm_id` (UNIQUE), `name`, `api_value` JSONB.
- Связи: `amo_customer_contact`, `amo_customer_company`, `amo_lead_contact`
  (составные PK, каскадное удаление).

Схема выдерживает поиск покупателя/сделки по точному логину и названию (b-tree индексы)
и связь сделка–покупатель (FK). Уникальность `crm_id` гарантируется БД, дублей
сущностей возникнуть не может.

### Алгоритм (`main.py`)

1. Предзагрузка индексов `crm_id/логин → abstract_customer.id` — 4 SELECT,
   весь матчинг дальше в памяти.
2. Покупатели и сделки читаются стримом из генератора `amocrm_get`:
   - покупатель без логина пропускается; поиск по id CRM, фолбэк по логину среди
     сделок; при >1 совпадении по логину совпадение не используется;
   - сделка ищется по id CRM, иначе по логину среди покупателей; две разные записи
     сливаются в найденную по сделке, вторая удаляется; не нашлось ничего —
     новая запись.
3. Запись батчами по 1000 строк: `INSERT ... ON CONFLICT (crm_id) DO UPDATE`
   (executemany), один COMMIT на пачку. Id новых агрегатов берутся из sequence
   БД батчами — identity map сессии не растёт.
4. Слияния применяются сеточными `UPDATE`/`DELETE` после загрузки.
5. Чистка после успешного полного прохода: ~10 SQL-выражений (связи — через
   временные таблицы пар, сущности — `NOT crm_id = ANY(:ids)` плюс «удалить»
   в названии, затем опустевшие агрегаты). Если сбор прервался или были ошибки
   обработки сущностей — чистка не запускается.

## Оценка ресурсов (20k покупателей / 50k сделок)

| | Было | Стало |
|---|---|---|
| Запросы к Postgres | ~300–400 тыс. (SELECT + UPDATE + COMMIT на каждую сущность, перечитка всей таблицы на чистке) | ~280 страниц API + ~10 SELECT на индексы + ~300–400 bulk-выражений (пачки по 1000) + ~10 на чистку |
| Память процесса | вся таблица с JSONB в `.all()` + identity map на весь прогон (сотни МБ и больше) | карты соответствий ~70k записей (десятки МБ) + текущая пачка ~1000 строк (~10 МБ); пик не зависит от объёма выгрузки |

## Что оставлено и почему

- Flask + Flask-SQLAlchemy и точка входа `collect_leads_customers(is_full=True)`.
- Фильтры по `status_id` (111349/143).
- Клиент `amocrm.py` как был (заглушка без авторизации); добавлены только
  отсутствовавшие `BaseEntity.as_dict()` и `BaseEntity.get_schema()` — без них
  клиент падал на первом же запросе, и разбор `_embedded`-контактов в
  `Lead.__init__` (как у `Customer`) — контакты сделок молча терялись.
- Формат сырых данных: полный ответ API лежит в `api_value` JSONB каждой сущности.
- Поведение при неоднозначном логине (>1 записи): совпадение не используется,
  создаётся новая запись — как в исходном коде.
